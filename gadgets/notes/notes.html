承認を観察する Gadget

Gadget が外の世界に触れると何が起きるかを見るための Gadget である。 counter.nw が Gadget 単体の仕組みを見る道具だったのに対して、 こちらは Gadget と Gatekeeper のあいだを見る。

見たいのは次の三つで、これは HANDOFF.md §5 手順2 が挙げた項目である。

- 承認待ちの操作が画面にどう出るか - 自動承認ルールを後から足したとき、待たされていた操作がその場で通るか - 読み取りが本当に承認を経ずに素通りするか

そのために、繋ぐ先には性質の違う三つの道具を用意してある。 接続先は tools/mockportal.mjs（このリポジトリに同梱の、依存のない MCP サーバ）で、 実害のある副作用は起こさない。メモに文字列を足すだけである。

なぜエージェントを使わないか

手順2 の原文は「副作用のある操作をエージェントにさせる」だったが、 エージェントは要らない。 承認待ちの記録を作る submitAction は 呼び出し元を選ばず、Gadget からの呼び出しもそこに含まれる。 §2.7 で使った「エージェントを迂回する」筋がここでも通る。

証言overseer.ts:6814from: "gadget";
推理overseer.ts:6810-6826呼び出し元は agent / gadget / user / hook の四つで、gadget はそのうちの一つ

三つの道具と、その期待される扱い

MCP のツールが「読み取り」か「承認の要る操作」かは、 サーバ自身が付けた注釈だけで決まる。判定は一箇所にまとまっていて、 すべて === true / === false の比較である。注釈のないツールは どの判定にも当たらず、承認の要る操作として扱われる。

さらに、自動承認を許されるのは注釈を信用してよい接続先だけである。 利用者が URL を貼る方式（byo）では、書き込みが自動で通ることは決してない。

| 道具 | 注釈 | 期待される扱い | |---|---|---| | notes_read | readOnlyHint: true | 観測。承認を経ずに走る | | notes_append | なし | 操作。常に手動の承認が要る | | notes_touch | destructiveHint: false, idempotentHint: true | 操作。自動承認ルールを作れる |

三つ目が要るせいで、接続先には gatekeeper-mcp ではなく gatekeeper-mcp-portal を使っている。前者は信用の段階が byo に固定されており、 自動承認が永久に成立しないためである。

自動承認は前の関門を越えない

ルールを作れば待っている保留がすぐ通る、とは限らない。

保留を適用する処理は、その gatekeeper の保留を **id の昇順に見て、 自動適用できないものに当たったらそこで止まる**。飛び越えない。 だから自動承認の資格を持つ保留でも、**それより前に人手の要る保留があれば、 順番が来るまで待たされる**。

実際にそうなった。notes_append（人手が要る）を先に、notes_touch（自動承認の 資格あり）を後に積んだ状態で notes_touch のルールを有効にしたところ、 何も起きなかった。前の関門で止まっていたためである。

止まっていた証拠は、関門を外したときに出た。notes_append を人手で承認すると、 その直後に notes_touch が誰にも聞かれずに走った。間隔は 233 ミリ秒で、 人間は一度しか押していない。承認が関門を外し、堰き止められていた保留が 続けて流れた形である。

UI の文言はこの場合を想定していない。 ルールを作るときの確認ダイアログは 「This action will be applied now too」と無条件に述べるが、 前に関門があれば適用されない。説明のほうが実装より大雑把だった。

自己申告を信じるということ

読み書きの判定はサーバの自己申告だけに依っている。署名も検証もない。 だから readOnlyHint: true と名乗る書き込みは、承認を経ずに走る。

これは見落としではなく、自覚して選ばれたトレードオフである。出典に そう書いてある——注釈を信じるのは「ただ得をする話ではない」、 サーバが誤ったラベルを付けたツールは承認なしで走る、と。

実際に嘘をつかせて確かめた。 notes_append に readOnlyHint: true を 名乗らせ、振る舞いは変えずに（書き込みはそのまま）押した。承認を求められず、 ok が返り、メモは書き換わった。

嘘は即座には効かない。 分類はカタログのキャッシュに乗っており、期限は 5 分である。名乗りを変えた直後は 古い分類のままで、承認を要求され続けた。期限が切れたあと最初の呼び出しで、 その呼び出し自身がカタログを取り直し、新しい分類がその場でその呼び出しに適用された。 取り直しから着信まで 129 ミリ秒、同じ往復の中である。

嘘は成立するが、記録は正直である。 プラットフォームは止めない。警告も出さない。代わりに**観測として記録し、 出所を明記する**——「サーバがこのツールを読み取りだと宣言しているので承認なしで走る。 その主張はサーバ自身によるものである」。

結果として、承認履歴に同じツールが二つの姿で並ぶ。正直だった頃の呼び出しは 盾のアイコンで「承認済み」、嘘のあとの呼び出しは目のアイコンで「観測」。 告発ではなく、並置による記録である。

ただし「記録に残る」ことと「誰かが気づく」ことは別である。 気づくには 履歴を見る人が要る。

回収

保留になった操作の結末は、番号を渡して取りに行く。 この呼び出しは待たない。 承認前に呼べば「まだ待っている」がそのまま返る。 人間が承認するまでポーリングする形になる。

承認済みの結果を受け取ると、それ自体が観測として記録される。 Gadget が見ていないあいだに走ったので、渡された時点で読んだことになるという理屈である。

三つの結末をすべて実機で見た。承認前・承認後・却下後で、返る文字列が違う。

| いつ回収したか | 返るもの | |---|---| | 承認前 | pending と is awaiting approval. | | 承認後 | ok と、サーバが返した中身 | | 却下後 | rejected と was not approved. |

承認前の文言が、呼び出したときの needs approval. Poll getActionResult(N) とは 別の文字列であることに注意する。同じ「待っている」でも、 呼んだ側に最初に返す文と、問い合わせに答える文は別に書かれている。

回収は問い合わせであって実行ではない。 承認前に回収しても、接続先には何も届かない。

そして予告どおり、承認済みの結果を受け取ると、それ自体が観測として記録された。 承認履歴に result of notes_append という独立した項目が現れ、 「承認された呼び出しの応答を読んだ」と書かれる。

物証2026-08-11承認後に回収すると ok とサーバの応答が返り、承認履歴に result of notes_append という観測が新たに現れた

記録の描画

一行ごとに、道具の名前と結果の状態を出す。 回収ボタンを付けるのは、道具を呼んだ記録が保留のときだけである。

当初は「保留かつ番号を持つ行」に付けていたが、回収の結果にもボタンが付いた。 回収の返りもまだ保留なら pending で番号も持つからである。ポーリングとしては 正しいが、押すたびに同じ見た目の行が増えるだけで読めない。種別で判定する。

古い記録には種別がないのでボタンは出ない。既に結末の出た保留ばかりなので 実害はないが、記録の形を変えると過去の記録が意味を失うという一例ではある。

状態によって色を変えておくと、承認の前後で何が変わったかが目で追える。

却下された行には取り消し線を引く。 色だけだと「赤い＝失敗した」と読めてしまうが、 却下は失敗ではなく実行されなかったことである（「観察した結果」）。 取り消し線は「なかったことになった」という意味に近く、そちらのほうが実態に合う。

この 4 行はエージェントが書いた。<<記録を描き直す>> という正しいチャンクを選び、 挿入位置も正確だった。ただし client.js の再生成はしていない——する手段がない。 tangle は人間が回した（HANDOFF.md §2.23）。

観察は三方向から取っている。画面に何が出たか、接続先のサーバに何が届いたか、 そして承認履歴に何が残ったかである。呼んだ側・呼ばれた側・記録係の三つで、 一つでも欠けると分からないことがある。

二つ目が効いた。「保留になった」ことは画面を見れば分かるが、 「まだ起きていない」ことは受け側を見ないと分からない。 三つ目は自己申告の実験で効いた。嘘が成立したことと、それが記録されたことは別の事実で、 後者は記録係の側にしか現れない。

- 承認待ちは Activity に Needs review として並ぶ。 なぜ操作として扱われたかの理由も文章で出る - 自動承認は効く。ただし前の関門を越えない（前節） - 読み取りは承認を経ない。押した瞬間にサーバへ届き、値が返った

承認と却下の非対称も、受け側の記録で見えた。 同じツール・同じ形の保留を 二つ積み、片方を承認、片方を却下した。承認したほうだけが接続先に届き、 却下したほうは一度も届かなかった。却下は「実行して取り消す」ではなく 「実行しない」である。どちらにも解決者の名前が残る。

却下は、二つの記録に違う形で残る。 承認履歴には「却下」として残るが、 接続先のログには何も残らない。届いていないのだから当然ではある。 だが裏を返すと、接続先の側からは「却下された操作があった」ことが見えない。 三方向のうち一方だけが知っている事実がある。

言えないことも書いておく。 試したのは利用者が繋いだ接続先の層であって、 管理者が上流を保証する層は触っていない。そして 「記録に残る」ことと「誰かが気づく」ことは別である。 気づくには履歴を見る人が要る。
