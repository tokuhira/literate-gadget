承認を観察する Gadget

Gadget が外の世界に触れると何が起きるかを見るための Gadget である。 counter.nw が Gadget 単体の仕組みを見る道具だったのに対して、 こちらは Gadget と Gatekeeper のあいだを見る。

見たいのは次の三つで、これは HANDOFF.md §5 手順2 が挙げた項目である。

- 承認待ちの操作が画面にどう出るか - 自動承認ルールを後から足したとき、待たされていた操作がその場で通るか - 読み取りが本当に承認を経ずに素通りするか

そのために、繋ぐ先には性質の違う三つの道具を用意してある。 接続先は tools/mockportal.mjs（このリポジトリに同梱の、依存のない MCP サーバ）で、 実害のある副作用は起こさない。メモに文字列を足すだけである。

なぜエージェントを使わないか

手順2 の原文は「副作用のある操作をエージェントにさせる」だったが、 エージェントは要らない。 承認待ちの記録を作る submitAction は 呼び出し元を選ばず、Gadget からの呼び出しもそこに含まれる。 §2.7 で使った「エージェントを迂回する」筋がここでも通る。

証言overseer.ts:6813from: "gadget";
推理overseer.ts:6809-6825呼び出し元は agent / gadget / user / hook の四つで、gadget はそのうちの一つ

三つの道具と、その期待される扱い

MCP のツールが「読み取り」か「承認の要る操作」かは、 サーバ自身が付けた注釈だけで決まる。判定は一箇所にまとまっていて、 すべて === true / === false の比較である。注釈のないツールは どの判定にも当たらず、承認の要る操作として扱われる。

さらに、自動承認を許されるのは注釈を信用してよい接続先だけである。 利用者が URL を貼る方式（byo）では、書き込みが自動で通ることは決してない。

| 道具 | 注釈 | 期待される扱い | |---|---|---| | notes_read | readOnlyHint: true | 観測。承認を経ずに走る | | notes_append | なし | 操作。常に手動の承認が要る | | notes_touch | destructiveHint: false, idempotentHint: true | 操作。自動承認ルールを作れる |

三つ目が要るせいで、接続先には gatekeeper-mcp ではなく gatekeeper-mcp-portal を使っている。前者は信用の段階が byo に固定されており、 自動承認が永久に成立しないためである。

書き足し

notes_append には注釈が一つも付いていない。したがって承認の要る操作になり、 接続先が信用されていても自動承認の対象にはならない。何度押しても手動の承認が要る、 というのがこの道具の役目である。

呼び出しはすぐ返ってくる。返ってくるのは結果ではなく pending と番号で、 実際に走ったかどうかはこの時点では分からない。

走っていないことを外から確かめた。 押した直後、接続先のサーバには 何も届いていなかった。承認 UI の説明文も 「Nothing has been sent yet」と述べている。呼び出しは gatekeeper の手前で 止められ、保留として積まれるだけである。

同じ pending から始まることに注意する。自動承認ルールを作る前は notes_append と見分けがつかない。違いが出るのはルールを足したあとである。

自動承認は前の関門を越えない

ルールを作れば待っている保留がすぐ通る、とは限らない。

保留を適用する処理は、その gatekeeper の保留を **id の昇順に見て、 自動適用できないものに当たったらそこで止まる**。飛び越えない。 だから自動承認の資格を持つ保留でも、**それより前に人手の要る保留があれば、 順番が来るまで待たされる**。

実際にそうなった。notes_append（人手が要る）を先に、notes_touch（自動承認の 資格あり）を後に積んだ状態で notes_touch のルールを有効にしたところ、 何も起きなかった。前の関門で止まっていたためである。

止まっていた証拠は、関門を外したときに出た。notes_append を人手で承認すると、 その直後に notes_touch が誰にも聞かれずに走った。間隔は 233 ミリ秒で、 人間は一度しか押していない。承認が関門を外し、堰き止められていた保留が 続けて流れた形である。

UI の文言はこの場合を想定していない。 ルールを作るときの確認ダイアログは 「This action will be applied now too」と無条件に述べるが、 前に関門があれば適用されない。説明のほうが実装より大雑把だった。

回収

保留になった操作の結末は、番号を渡して取りに行く。 この呼び出しは待たない。 承認前に呼べば「まだ待っている」がそのまま返る。 人間が承認するまでポーリングする形になる。

承認済みの結果を受け取ると、それ自体が観測として記録される。 Gadget が見ていないあいだに走ったので、渡された時点で読んだことになるという理屈である。

この経路だけは実機で走らせていない。 回収ボタンが保留の行に出るところまでは 確かめたが、押していない。承認が済んだあとに結果を取りに行く往復は、 コードを読んで書いたままの状態である。

記録の描画

一行ごとに、道具の名前と結果の状態を出す。 保留のものには回収ボタンを付ける。番号を持っているのは保留の行だけである。

状態によって色を変えておくと、承認の前後で何が変わったかが目で追える。

物証2026-08-10ok は緑、pending は橙で表示され、pending の行にだけ回収ボタンが出た

<<記録を描き直す>>=

const COLOR = {
  ok: "#0a0", pending: "#c60", rejected: "#c00", failed: "#c00",
};

function render(log) {
  table.textContent = "";
  for (const row of [...log].reverse()) {
    const line = document.createElement("div");
    line.style.cssText = "padding:.25rem 0;border-top:1px solid #ddd";

    const status = document.createElement("b");
    status.textContent = row.status;
    status.style.color = COLOR[row.status] ?? "#666";

    const label = document.createElement("span");
    label.textContent = ` ${row.tool} — ${row.detail ?? ""}`;

    line.append(status, label);
    if (row.status === "pending" && row.actionId !== undefined) {
      line.append(button("回収", () => gadget.collect(row.actionId)));
    }
    table.append(line);
  }
}

観察した結果

冒頭に挙げた三つは実機で見た。上の表の「期待される扱い」は期待ではなくなった。

観察は二方向から取っている。画面に何が出たかと、接続先のサーバに何が届いたかである。 後者が効いた。「保留になった」ことは画面を見れば分かるが、 「まだ起きていない」ことは受け側を見ないと分からない。

- 承認待ちは Activity に Needs review として並ぶ。 なぜ操作として扱われたかの理由も文章で出る - 自動承認は効く。ただし前の関門を越えない（前節） - 読み取りは承認を経ない。押した瞬間にサーバへ届き、値が返った

物証2026-08-10画面の表示とモックサーバの着信ログを突き合わせ、三項目すべてを確認した

それでも確かめていないこと

- 回収の往復。 保留の結果を取りに行く経路は走らせていない - 注釈が嘘だった場合。 読み書きの判定はサーバの自己申告に依存する。 readOnlyHint を偽って付けた書き込みは、承認を経ずに走るはずである。 起きないことを確かめたのではなく、起きうる構造だと確かめたにすぎない。 ここは自前のサーバで嘘をつかせれば試せるが、まだやっていない - 却下したときの経路。 Deny は一度も押していない
