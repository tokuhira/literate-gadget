共有カウンタ Gadget

これは Cloudflare OS の Gadget を文芸的プログラミングで書いた例である。 複数のブラウザから同じ数値を増減でき、誰かが押したら全員の画面が即座に更新される。

Gadget は必ず二つのファイルからなる。server.js はサーバ側、client.js はブラウザ側で、その二つが <<...>> の記法で一つの文書から取り出される。 以下では先に全体の形を述べ、細部はあとまわしにする。

サーバ側の全体像

サーバは Durable Object という Cloudflare の仕組みで、 一つの Gadget インスタンスにつき一つだけ存在するサーバオブジェクトである。 状態を持ち、複数のブラウザからの接続を同時に相手にする。

クラス名は必ず Gadget でなければならない。

購読者の集合

「誰かが押したら全員の画面が更新される」を実現するために、 接続中のブラウザから預かったコールバックを保持しておく。 これはメモリ上の集合でよい。接続が切れれば意味を失う情報だからである。

constructor(ctx, env) {

現在値

数値そのものはメモリではなく Durable Object のストレージに置く。 サーバはいつ再起動してもよいことになっており、 メモリに置いた値は再起動で消えてしまうからである。

まだ一度も押されていなければ値は存在しないので、そのときは 0 とみなす。

物証2026-08-07コードを書き換えて再デプロイさせたあとも、リロードすれば数値は保たれていた
証言agent.ts:468ALWAYS store server state in Durable Object storage, not just in memory

<<現在値を読む>>=

async getCount() {
  return (await this.ctx.storage.get("count")) ?? 0;
}

増減

読んで、足して、書き戻して、全員に知らせる。 delta には +1 か -1 が来る。

物証2026-08-07ボタンで増減し、もう一方のウィンドウへ即座に伝わった

<<値を増減する>>=

async increment(delta) {
  const next = (await this.getCount()) + delta;
  await this.ctx.storage.put("count", next);
  this.broadcast(next);
  return next;
}

購読

ブラウザは自分のコールバックをサーバに渡す。ここが Cap'n Web の面白いところで、 関数そのものを RPC で渡せる。受け取った側には呼び出し可能なスタブが届く。

ただし渡ってきたスタブは、このメソッドを抜けた時点で自動的に破棄される。 長く持ち続けるには .dup() で複製を取らなければならない。 また、ブラウザが閉じられたことは onRpcBroken で通知されるので、 そこで集合から取り除く。

物証2026-08-07二つのウィンドウで同時に開き、片方のボタンが即座にもう片方へ反映された
証言agent.ts:431it is important to call .dup() on the callback stub, in order to obtain a long-lived stub

<<更新の購読を受け付ける>>=

async subscribe(callback) {
  const held = callback.dup();
  this.subscribers.add(held);
  held.onRpcBroken(() => this.subscribers.delete(held));
  return this.getCount();
}

配信

集合を舐めて全員に伝えるだけ。 途中で切れた接続があっても他の配信を止めたくないので、失敗は握り潰す。

この catch が到達可能であることは確かめた。 onRpcBroken を外した 実験用の Gadget を作り、切れた購読者を集合に残したまま配信したところ、 配信のたびにちょうど 1 回ずつ失敗が記録された。到達不能な死んだコードではない。

ただし本番の隙間で発火するところは見ていない。 本番では onRpcBroken が購読者を取り除くので、update が失敗するのは 「切断が起きてから取り除かれるまでの隙間」に限られる。 その隙間を狙って観察する方法はまだない。

握り潰す判断は保険として妥当だと考えているが、 保険が要る状況が実際に起きるかどうかは、まだ別の問題である。

物証2026-08-09onRpcBroken を外した実験用 Gadget で、切れた購読者を集合に残したまま 3 回配信したところ失敗が 0 から 3 に増えた

<<全員に配信する>>=

broadcast(count) {
  for (const s of this.subscribers) {
    s.update(count).catch(() => {});
  }
}

更新の受け取り

サーバに渡すコールバックは RpcTarget を継承したオブジェクトとして作る。 サーバが s.update(count) を呼ぶと、ここの update が走る。

[Symbol.dispose] は接続が切れたときに呼ばれる。 やることは接続しなおすことだけなので、次節の connect に任せる。

なお公式の例は同じオブジェクトを渡し直す（gadget.subscribe(this)）が、 ここでは new Watcher() を作り直している。破棄されたオブジェクトを 再び渡すより素直だと考えたためで、どちらが正しいかは確かめていない。

証言agent.ts:460other capabilities passed over RPC in either direction are disposed on disconnect, and must be re-acquired
証言agent.ts:452Connection lost. Resubscribe using new connection.

<<サーバからの更新を受け取る>>=

class Watcher extends RpcTarget {
  update(count) {
    display.textContent = count;
  }

  [Symbol.dispose]() {
    connect();
  }
}

接続と再接続

購読を申し込むと現在値が返ってくるので、それを表示にする。 subscribe が現在値を返す設計にしてあるおかげで、 「購読する」と「現在値を取る」を一往復で済ませられる。

この一往復を関数にまとめておくと、起動時と再接続時で同じ処理を使える。 再接続のときも現在値を取り直せることが重要で、 切れているあいだに他の誰かが押していれば、画面の数字はもう古い。

ここでは再接続を自前で作らない。 一度作って失敗している。 gadget への呼び出しは、失敗しても例外を投げずに待ち続けるので、 try / catch では何も捕まらない。書いたリトライは一度も実行されなかった。

待つ理由は、gadget が親フレーム側の Proxy で、 再接続中の呼び出しを保留する作りになっているからである。 保留を解除するのも、駄目なら iframe を再読み込みするのも、 プラットフォームの側が既にやっている。こちらで重ねて実装するものではない。 

<<接続する>>=

async function connect() {
  display.textContent = await gadget.subscribe(new Watcher());
}
